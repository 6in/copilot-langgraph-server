# Plan 09-02: OrchestratorHandler + API mode routing + Docker env

**Phase:** 09 - SuperChat OrchestratorGraph App Integration

## Context

The existing worker uses a pluggable `TASK_HANDLERS` dict with `TaskHandler` ABC. Adding the orchestrator is a clean extension: create `OrchestratorHandler(TaskHandler)`, register it as `task_type="orchestrator"`, and translate `mode='super'` to `task_type='orchestrator'` in the chat route before enqueuing. The Docker env vars ensure the worker can locate `agents/` and `menus/` inside containers.

Per research findings, the arq worker runs in a separate process and cannot access `app.state`. The `OrchestratorHandler` constructs `SubAgentRegistry` and compiles the graph per job -- this is fast (just reading AGENT.md files from disk) and correct for multi-user token isolation. No lifespan changes needed for the orchestrator graph (skipping D-05's `app.state.orchestrator_graph` approach per research recommendation).

## Tasks

### Task 1: Create OrchestratorHandler

**Files:** `app/jobs/handlers/orchestrator_handler.py`
**Action:** create

Create `OrchestratorHandler(TaskHandler)` following the exact same pattern as `LangGraphHandler`:

```python
"""OrchestratorGraph task handler — routes user input through SubAgent routing."""
import os
import logging

from app.jobs.handlers.base import TaskHandler
from app.jobs.notifier import build_notifier
from app.orchestrator.agent import SubAgentRegistry
from app.orchestrator.graph import build_orchestrator_graph
from app.orchestrator.state import AgentState

logger = logging.getLogger(__name__)

AGENT_DIR = os.getenv("AGENT_DIR", "./agents")


class OrchestratorHandler(TaskHandler):
    """Handles task_type="orchestrator": builds OrchestratorGraph per job and routes input."""

    async def handle(self, ctx: dict, job: dict) -> dict:
        job_id: str = job["job_id"]
        prompt: str = job["prompt"]
        github_token: str = job["github_token"]
        model: str = job.get("model", "claude-sonnet-4.5")
        reply_to: dict = job["reply_to"]

        job_store = ctx["job_store"]
        notifier = build_notifier(reply_to, job_store)

        try:
            await notifier.progress("thinking")

            # Construct registry and graph per job (fast: reads AGENT.md from disk)
            # github_token is threaded so each user gets their own Copilot session
            registry = SubAgentRegistry(AGENT_DIR, github_token)
            if not registry.agents:
                raise RuntimeError(
                    f"No agents found in AGENT_DIR={AGENT_DIR}. "
                    "Check that agents/ directory exists and contains AGENT.md files."
                )

            graph = build_orchestrator_graph(registry, github_token)

            initial: AgentState = {
                "input": prompt,
                "output": "",
                "messages": [],
                "next": "",
            }
            result = await graph.ainvoke(initial)
            final_text = result["output"]

            await job_store.save_result(job_id, final_text)
            await notifier.done()

        except Exception as e:
            logger.exception("OrchestratorHandler failed for job %s", job_id)
            await job_store.save_result(job_id, f"Error: {e}")
            await notifier.done()

        return {"job_id": job_id, "status": "done"}
```

Key differences from `LangGraphHandler`:
- No `thread_id` / checkpointer usage (orchestrator is stateless per research -- deferred to future phase)
- Uses `SubAgentRegistry(AGENT_DIR, github_token)` instead of `ChatCopilot` directly
- Extracts `result["output"]` instead of `result["messages"][-1].content`
- Guards against empty registry with `RuntimeError`
- No `llm.close()` needed (SubAgent instances are short-lived)


## Notes

- The orchestrator graph is constructed per job, not at startup. This avoids the `app.state` sharing problem (arq worker is a separate process) and ensures each user gets their own `github_token`-scoped ChatCopilot instances. The overhead is negligible (reading a few AGENT.md files from disk).
- `task_type` vs `mode` field overlap: `mode` takes priority for routing. If `mode=='super'`, `task_type` is overridden to `'orchestrator'` regardless of what `task_type` was set to. If `mode=='simple'`, `task_type` is used as-is (defaults to `'langgraph'`). This maintains backward compatibility with any clients that set `task_type` directly.
- Super-mode conversations have no persistent history (no checkpointer). This is explicitly deferred per CONTEXT.md.
