4 つの bash ファイルを作成する。すべて `#!/usr/bin/env bash` + `set -euo pipefail` + shellcheck clean (SC2086 等の頻出は明示的に対処) を満たすこと。`scripts/lib/backup-common.sh` の関数を他 3 スクリプトが `source` する。Python は使わず host 側に依存させない (pg_dump / psql はすべて `docker compose exec postgres` 経由)。

【scripts/lib/backup-common.sh — 共通ヘルパー】
- 役割: env (dev|prod) を引数で受け取り、compose project name / compose file flag / volume prefix を解決する関数群。
- 提供関数:
  - `resolve_env "$ENV_NAME"` → グローバル変数を export:
    - `COMPOSE_PROJECT` ("copilot-langgraph" or "copilot-langgraph-prod")
    - `COMPOSE_FILES` ("-f docker-compose.yml" or "-f docker-compose.prod.yml")
    - `VOL_POSTGRES` ("${COMPOSE_PROJECT}_postgres-data" or "${COMPOSE_PROJECT}_postgres-data-prod")
    - `VOL_THREAD_FILES` (同様の規則で thread-files / thread-files-prod)
    - `VOL_CLAUDE_OUT` (同様の規則で claude-code-outputs / claude-code-outputs-prod)
  - `log "<msg>"` → `[YYYY-MM-DD HH:MM:SS] <msg>` を stderr に出力 (緑色 ANSI)
  - `warn "<msg>"` → 同上 (黄色)
  - `err "<msg>"` → 同上 (赤) かつ exit 1
  - `confirm "<prompt>"` → -y フラグ (グローバル `ASSUME_YES=1`) が立っていれば即 return 0、そうでなければ read で y/N を尋ねて Y/y のみ続行
  - `require_cmd <cmd>` → `command -v` で確認、無ければ err
  - `compose <args...>` → `docker compose -p "$COMPOSE_PROJECT" $COMPOSE_FILES "$@"` を実行するラッパー
- volume 名のプレフィックス検証: `docker volume ls --format '{{.Name}}'` で実際に存在するかを resolve_env 内で検証し、無ければ err でその旨を伝える。

【scripts/db-backup.sh — バックアップ】
- 引数:
  - `--env dev|prod` (default: dev)
  - `--out <dir>` (default: ./backups)
  - `--stop-services` (任意: api/worker を一時停止してから dump する)
  - `--no-compress` (任意: gzip 圧縮を省略 — debug 用)
  - `-y` / `--yes` (確認スキップ — このスクリプトでは確認は出さないが互換のため受け取る)
- フロー:
  1. `resolve_env` で env 解決
  2. `STAMP=$(date -u +%Y%m%d-%H%M%S)`、`DEST="$OUT_DIR/$STAMP"` を作成
  3. `--stop-services` 指定時: `compose stop api worker` (postgres と mcp-server は残す)
  4. PostgreSQL ダンプ: `compose exec -T postgres pg_dump -U postgres --no-owner --no-comments --no-publications --no-subscriptions postgres` を `gzip` に pipe して `$DEST/postgres.sql.gz` に保存。`set -o pipefail` の効果で pg_dump 失敗時に exit 1 になることを確認。
  5. thread-files volume を tar: `docker run --rm -v "$VOL_THREAD_FILES:/data" -v "$DEST:/backup" busybox sh -c 'cd /data && tar czf /backup/thread-files.tar.gz .'`。volume が空でも空 tar を作る (find /data -mindepth 1 で空判定して 0 byte ファイルにしてもよい)。
  6. claude-code-outputs volume を同様に `claude-code-outputs.tar.gz` へ。
  7. Canvas 静的ファイル: ホスト側 `./static/apps/` が存在すれば `tar czf "$DEST/canvas-static.tar.gz" -C ./static apps/` で集約。存在しなければ skip (warn のみ)。
  8. `--stop-services` 指定なら最後に `compose start api worker`
  9. `$DEST/MANIFEST.json` を生成:
     ```
     {
       "timestamp": "<ISO8601 UTC>",
       "env": "<dev|prod>",
       "compose_project": "<COMPOSE_PROJECT>",
       "volumes": {
         "postgres": "<VOL_POSTGRES>",
         "thread_files": "<VOL_THREAD_FILES>",
         "claude_code_outputs": "<VOL_CLAUDE_OUT>"
       },
       "files": {
         "postgres.sql.gz":          { "size": <bytes>, "sha256": "<hex>" },
         "thread-files.tar.gz":      { "size": <bytes>, "sha256": "<hex>" },
         "claude-code-outputs.tar.gz": { "size": <bytes>, "sha256": "<hex>" },
         "canvas-static.tar.gz":     { "size": <bytes>, "sha256": "<hex>" }
       },
       "restore_cmd": "./scripts/db-restore.sh ./backups/<STAMP> --env <env>"
     }
     ```
     `sha256sum` と `stat -c '%s'` を使う。`canvas-static.tar.gz` が無ければ files から省く (null ではなく key 自体を出さない)。
 10. log で完了サマリを表示: 各ファイルサイズと合計、保存先パス。
- 失敗時の clean-up: trap で `rm -rf "$DEST"` を ERR にバインドし、途中失敗で中途半端なディレクトリを残さない。

【scripts/db-restore.sh — リストア】
- 引数:
  - `<backup-dir>` (positional、必須)
  - `--env dev|prod` (default: backup-dir の MANIFEST.json から推定。マニフェスト無ければ要明示)
  - `-y` / `--yes` (確認プロンプトを skip)
  - `--no-canvas-rebuild` (任意: dual-source rebuild ステップを skip — debug 用)
- フロー:
  1. backup-dir 存在チェック、MANIFEST.json 読み取り (jq があれば使い、無ければ python3 -c も使わず sed/grep で env を抽出 — fallback として `jq` 必須を明示するほうが単純なら `require_cmd jq` でよい)
  2. `resolve_env`
  3. `confirm "Restore will WIPE current data in env=$ENV (volumes: $VOL_POSTGRES, $VOL_THREAD_FILES, $VOL_CLAUDE_OUT and host ./static/apps/). Continue?"` で確認
  4. `compose down` で api/worker/mcp-server/postgres を全停止 (volume は残す)
  5. volume 削除 + 再作成:
     - `docker volume rm "$VOL_POSTGRES" "$VOL_THREAD_FILES" "$VOL_CLAUDE_OUT"` (無視できないエラーは err)
     - `compose up -d postgres` で postgres を上げる (`docker-entrypoint-initdb.d` の `01-enable-pgvector.sql` が初回起動で流れる前提)
     - postgres healthcheck 待ち: `compose exec -T postgres pg_isready -U postgres` を retry 30 回・1 秒間隔で待機
  6. PostgreSQL リストア:
     ```
     gunzip -c "$DEST/postgres.sql.gz" | compose exec -T postgres psql -U postgres -d postgres
     ```
     pipefail で失敗検知。psql の終了コードが 0 でなくても続行せず err。
  7. thread-files / claude-code-outputs volume へ展開:
     ```
     docker run --rm -v "$VOL_THREAD_FILES:/data" -v "$DEST:/backup" busybox sh -c 'cd /data && tar xzf /backup/thread-files.tar.gz'
     ```
     claude-code-outputs.tar.gz も同様。
  8. Canvas 静的ファイル復元:
     - `canvas-static.tar.gz` が存在すれば `tar xzf "$DEST/canvas-static.tar.gz" -C ./static/` で展開
     - 存在しなければ warn のみで次へ
  9. Canvas dual-source rebuild (`--no-canvas-rebuild` 指定時は skip):
     - `compose exec -T postgres psql -U postgres -d postgres -tAc "SELECT app_id, html FROM canvas_apps WHERE deployed = true"` の結果を読む
     - ※ html 列は改行/null を含むので、psql `-tAc` の生出力では使えない。`COPY (SELECT app_id, encode(convert_to(html, 'UTF8'), 'base64')) FROM canvas_apps WHERE deployed = true TO STDOUT` で 1 行 1 app_id\tbase64 形式に整形して取得し、bash で読みつつ `base64 -d` して `./static/apps/<app_id>/index.html` に書き出す。
     - 既に存在する `./static/apps/<app_id>/index.html` は上書き OK (canvas-static.tar.gz から展開した内容を DB から再生成して整合させる)。
     - app_prefix の `$URL_PREFIX` 置換は deploy 時点で済んだ HTML が DB に格納されている前提だが、`canvas.py` 実装を読むと html 列には置換 *前* が入っているので、APP_PREFIX env を読んで rebuild 時にも同じ置換を適用する: `${APP_PREFIX:-}` を取得して `sed "s|\$URL_PREFIX|$APP_PREFIX|g"` で書き出す。
  10. `compose up -d` で全サービス再開
  11. 完了サマリ: rebuild した canvas app 数、復元したファイル合計サイズを log

  4. 何個削除したかと残数を log

# バックアップ/リストア運用ガイド

## 概要
- 対象 3 層 (PostgreSQL / Worker 生成ファイル volume / Canvas 静的デプロイファイル) と、なぜ 3 層必要かを 2-3 行で説明 (特に Canvas は DB と FS の dual-source なので片方では復元できない、を明記)

## バックアップ対象
- 表形式で:
  | 層 | dev volume / path | prod volume / path | 保存ファイル名 |
  |---|---|---|---|
  | PostgreSQL | postgres-data | postgres-data-prod | postgres.sql.gz |
  | Worker thread files | thread-files | thread-files-prod | thread-files.tar.gz |
  | Worker claude-code outputs | claude-code-outputs | claude-code-outputs-prod | claude-code-outputs.tar.gz |
  | Canvas 静的デプロイ | ./static/apps/ (bind mount) | 同左 | canvas-static.tar.gz |
- バックアップ対象外: `redis-data` / `redis-data-prod` (ジョブキュー・キャッシュなので再構築可)
- 監査ログ / agent_traces / canvas_apps テーブルは PostgreSQL ダンプに含まれる

## バックアップ手順

### 基本 (dev)
```
./scripts/db-backup.sh
```
→ `./backups/YYYYMMDD-HHMMSS/` に 4 ファイル + MANIFEST.json が作成される

### prod 環境
```
./scripts/db-backup.sh --env prod
```

### サービス停止モード (DB 書き込み中の整合性を最大化)
```
./scripts/db-backup.sh --stop-services
```
→ 実行中は api/worker が止まる (postgres と mcp-server は稼働継続)。pg_dump は MVCC で snapshot を取るので通常は不要だが、worker が大量書き込みしている時間帯は推奨。

### 出力例
- ファイルツリーと MANIFEST.json サンプルを示す

## リストア手順
- まず必ず最新バックアップが手元にあることを確認 (バックアップなしでリストアは不可)

### dev
```

```

### prod
```
./scripts/db-restore.sh ./backups/20260514-051200 --env prod
```
※ 通常は MANIFEST.json から env を自動推定するので明示不要。

### Canvas dual-source rebuild
- リストアの最終ステップで `canvas_apps.deployed = true` の全レコードを DB から SELECT し、`./static/apps/<app_id>/index.html` を書き戻す

- skip したい場合 (canvas-static.tar.gz の内容のみで十分な場合) は `--no-canvas-rebuild`

## トラブルシューティング
- **`docker volume rm` で "volume in use"**: `compose down` が走らなかったケース。手動で `docker compose -p copilot-langgraph down` (または prod 用) を実行してから再試行。
- **pg_dump で permission denied**: postgres コンテナが立ち上がっていない可能性。`docker compose ps postgres` で healthy 確認。
- **canvas rebuild 後にアプリが 404**: `APP_PREFIX` 環境変数が未設定で `$URL_PREFIX` の置換が空文字になっている可能性。`export APP_PREFIX=/orochi` してから再実行 (または `static/apps/<app_id>/index.html` を直接編集)。
- **`./backups/` を別ホストへ運ぶ**: `tar czf backups-snapshot.tar.gz backups/<dir>/` でディレクトリごと圧縮して転送するだけで OK。restore 側で展開した後 `./scripts/db-restore.sh ./backups/<dir>` を実行する。
