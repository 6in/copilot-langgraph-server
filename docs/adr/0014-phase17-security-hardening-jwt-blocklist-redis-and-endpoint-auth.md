# 0014. Phase 17 セキュリティ強化 — JWT ブロックリスト Redis 移行と未認証エンドポイントの修正

**Date:** 2026-04-07  
**Status:** Accepted

## Context

Phase 17（DebateChatApp）のコードレビューで、認証・認可に関する複数の脆弱性が発見された。

1. **JWT ブロックリストがインメモリ** — ログアウト後に発行された無効トークンのブロックリストが Python プロセスのメモリ上にあったため、arq worker プロセスや再起動後にリストが失われ、ログアウト済みトークンが再利用可能になっていた。
2. **SSE ストリームエンドポイントが未認証** — `GET /api/job/{id}/stream` は認証なしでアクセス可能だったため、job ID を知るだけで他ユーザーの SSE ストリームを盗聴できた。
3. **ジョブステータスポーリングが未認証** — `GET /api/job/{id}` も同様に認証なし。
4. **スレッド rename に所有者チェックなし** — `PATCH /api/threads/{id}` でユーザー認証は行うが、スレッドの所有者確認をしていなかったため、他ユーザーのスレッド名を書き換えられた。
5. **CORS がハードコード** — 開発用オリジン（`localhost:5173` 等）が本番環境にも適用されていた。

## Decision

### CR-04: JWT ブロックリストを Redis へ移行

`auth/jwt_utils.py` のインメモリ `set` を廃止し、Redis の `SETEX` コマンドでトークン JTI を TTL 付きで保存する方式に変更。

```python
# 旧: インメモリ
_blocklist: set[str] = set()

# 新: Redis SETEX (TTL = トークン残存有効期限)
redis_client.setex(f"blocklist:{jti}", ttl_seconds, "1")
```

TTL にトークンの残存有効期限を設定することで、自動的にガベージコレクションされる。Redis はすでに arq worker のブローカーとして Docker Compose に含まれており、追加インフラ不要。

### CR-01/CR-02: SSE・ポーリングエンドポイントへの JWT 認証追加

`GET /api/job/{id}/stream` と `GET /api/job/{id}` の両エンドポイントに `verify_token` 依存を追加。加えて、job の `user_id` とリクエストユーザーが一致するかを確認することでジョブ所有者チェックを実装。

### WR-02: rename_thread に所有者チェック追加

`PATCH /api/threads/{id}` の UPDATE クエリに `AND user_id = %s` 条件を追加。UPDATE が 0 行の場合は 403 を返す。

### WR-01: CORS_ORIGINS 環境変数による上書き

`main.py` の CORS origins を `CORS_ORIGINS` 環境変数から読み込み可能にした。未設定時は従来の開発用ハードコードにフォールバック。

## Alternatives Considered

### Redis の代わりに PostgreSQL でブロックリスト管理

JTI を `revoked_tokens` テーブルで管理する案。TTL の自動削除がないため定期クリーンアップジョブが必要になる。Redis はすでにインフラに含まれており、SETEX で TTL が自動管理されるため採用しなかった。

### SSE エンドポイントを WebSocket に変更して認証強化

WebSocket はハンドシェイク時に認証できる。しかしフロントエンドの SSE 実装を全面変更するコストが高く、今回の修正（ヘッダー経由の JWT 検証）で十分なため採用しなかった。

## Consequences

### 正の影響

- JWT ブロックリストが再起動・マルチプロセスをまたいで有効になった。ログアウト後のトークン無効化が確実に機能する
- SSE・ジョブポーリングで認可されていないユーザーが他ユーザーのジョブ結果を取得できなくなった
- スレッドのクロスユーザー書き換えが防止された
- CORS を環境変数で制御できるようになり、開発・本番で設定を分離できる

### 注意点・落とし穴

**1. Redis 接続が落ちると認証が完全停止する**  
JWT 検証時に Redis への疎通が必要になったため、Redis がダウンするとブロックリスト確認が失敗し認証エラーになる。Redis の可用性確保が認証の前提条件になった。フォールバック（Redis エラー時はブロックリスト確認をスキップ）を入れるかは運用ポリシーで判断が必要。

**2. TTL の計算にクロック同期が必要**  
JTI の TTL はトークンの `exp` クレームから `now` を引いた値で設定する。サーバーとコンテナのクロックがずれると TTL が負になり `SETEX` がエラーになる。`exp - time.time()` が 0 以下の場合は即座に 401 を返す前処理が必要（実装済み）。

**3. 新しいジョブエンドポイントを追加する際は所有者チェックを必ず実装する**  
今回の修正でパターンが確立された。`GET /api/job/{id}` 系のエンドポイントは `verify_token` + `job["user_id"] == current_user` の2段階チェックをテンプレートとして使うこと。
